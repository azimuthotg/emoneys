## บั๊กที่พบระหว่างอ่านโค้ด (ยังไม่แก้ — เข้าคิว `next:` แล้ว)

1. **race condition ตอนออกเลขที่ใบสำคัญ** — `transaction.atomic()` ใน
   `Receipt.generate_receipt_number()` ปิดก่อน INSERT จริง lock เลยหลุด

   ประเมินความรุนแรงเพิ่มเติมแล้วพบว่า**แคบกว่าที่คิดตอนแรก** เพราะมีตาข่ายรองรับ 2 ชั้นอยู่แล้ว:
   `unique_together = (receipt_number, department)` ที่ระดับ DB และ `receipt_save_ajax`
   ที่ดัก `IntegrityError` แล้วตอบ 409 ให้ผู้ใช้ลองใหม่
   รูรั่วจริงเหลือเฉพาะกรณี **หน่วยงานคนละ row ที่ใช้ `Department.code` เดียวกัน**
   (แชร์เล่มและลำดับเลขกัน แต่ constraint ไม่ยิงเพราะ department ต่างกัน)
   วัดจากฐาน test: มีรหัสที่แชร์กันแค่ `PO` (4 หน่วยงาน) กับ `EDU` (2) และยังไม่มีเลขซ้ำใน 112 ใบ
   → โอกาสต่ำ ผลกระทบสูง ควรแก้ในรอบนี้แต่ไม่ถึงขั้นต้องรีบ

   อีกจุดที่เกี่ยวกัน: `receipt_complete_draft_ajax` เรียก `receipt.save()` เปล่า ๆ
   ไม่ได้ดัก `IntegrityError` เลย ถ้าชนกันบนเส้นทางนี้จะได้ 500 แทนข้อความให้ลองใหม่
2. **`last_document_number` นับไม่ตรง** — ตอนอัปเดตกรอง department เดียว
   แต่ตอนออกเลขกรองทุก department ที่ใช้ code เดียวกัน
3. **Permission choices หลุด sync** — `receipt_cancel_approve` / `..._manager`
   ถูกใช้งานและสร้างลง DB แต่ไม่มีใน `Permission.PERMISSION_TYPES`
4. `EMAIL_BACKEND` เป็น console บน production → อีเมลแจ้งเตือนไม่ออกจริง
5. `pywebpush` + ฟิลด์ push subscription มีอยู่ แต่ไม่มีโค้ดส่งเลย

## เจอของสำคัญ 3 อย่าง

**1. prod รันด้วย `DEBUG=True`** — และแก้ตรง ๆ ไม่ได้ เพราะ static/media ถูกเสิร์ฟในบล็อก
`if settings.DEBUG:` ของ `urls.py` ส่วน `SECURE_SSL_REDIRECT` อยู่ในบล็อก `if not DEBUG:` ของ settings
ปิด DEBUG เฉย ๆ จะได้ static 404 ทั้งหมด **บวกกับ** redirect ไป https ที่ไม่มีอยู่
ต้องทำเป็นชุด: `ensurepip` → whitenoise → แยก `SECURE_SSL_REDIRECT` ออกมาตั้งเอง → ค่อยปิด DEBUG

**2. venv ไม่มี pip** — Django 4.2.25 อยู่ครบใน `emoney_env\Lib\site-packages`
(`include-system-site-packages = false`) แต่ `pip list` เงียบสนิท ต้องกู้ pip ก่อนติดตั้งอะไร

**3. เลขที่ใบสำคัญไม่เคยซ้ำจริง** — **0 คู่ จาก 10,484 ใบ** บนข้อมูล production
ทั้งที่รหัส `PO` ถูกแชร์ถึง 9 หน่วยงาน (ฐาน test มีแค่ 4) → ปรับ race condition
ลงเป็น "ควรแก้ ไม่เร่งด่วน" ได้อย่างมีหลักฐาน

## ข้อสรุประหว่างทางที่ผิดแล้วแก้แล้ว

ตอนเห็น `python.exe` 2 ตัวที่มี command line เหมือนกันสั่ง bind port 80 เหมือนกัน
เคยสรุปว่ามีเซิร์ฟเวอร์ 2 ชุดและตัวหนึ่งข้าม venv — **ไม่จริง**
พอตรวจ `ParentProcessId` กับ `Get-NetTCPConnection` พบว่าเป็นสายเดียวกัน
`services.exe → nssm.exe → venv python (3568) → C:\Python312 python (3600)` โดยตัวลูกถือ port 80
เป็นพฤติกรรมปกติของ venv บน Windows ที่ `Scripts\python.exe` ไป exec interpreter จริง
แต่คงค่า `sys.prefix` ของ venv ไว้ ระบบรันจาก venv ถูกต้องอยู่แล้ว

## แก้เอกสารฝั่ง nms_agent ด้วย

`C:\projects\nms_agent\docs\projects\emoneys.md` แก้ path เป็น `C:\emoneys` แล้ว
พร้อมเติมหัวข้อการรัน/deploy, หมายเหตุเรื่อง python 2 process, venv ไม่มี pip และกับดัก DEBUG
**ยังไม่ได้ commit** เพราะ git ที่นั่นฟ้อง dubious ownership — แจ้งไว้ใน `next:` ของ nms_agent แล้ว
ให้ฝั่งนั้นมาเก็บเอง

## สรุปภาคเช้า

commit ทั้งหมด 5 ตัว push ขึ้น `origin/main` แล้ว **ไม่มีบรรทัดไหนแตะโค้ดแอปเลย**

## 7. MySQL บล็อกทุก host ที่มาจากนอกเครื่อง

**อาการ** DBeaver ต่อฐาน prod จากข้างนอกไม่ได้
`Host '110.78.83.1' is blocked because of many connection errors`

**ไม่ใช่ firewall** — พิสูจน์ได้เพราะ error นี้เป็นคำตอบที่ MySQL ส่งกลับมาเอง
แปลว่า TCP วิ่งถึง MySQL process แล้ว ถ้า firewall บล็อกจะได้ timeout หรือ connection refused

**ต้นตอจริง** อุปกรณ์ที่ขา `110.78.83.0/25` ทำ SNAT ยุบทุก connection จากนอกเครื่อง
ให้เป็น IP เดียวคือ `110.78.83.1` (gateway) MySQL จึงนับ error ของทุกคนรวมกันในถังเดียว
พอชน `max_connect_errors` ที่เป็นค่า default **100** ก็บล็อก = **คนนอกเข้าไม่ได้พร้อมกันทั้งหมด**

ตัวเลขจาก `performance_schema.host_cache`:

| ค่า | ผล |
|---|---|
| `SUM_CONNECT_ERRORS` | 101 |
| `COUNT_HANDSHAKE_ERRORS` | **101** ← ตรงกันเป๊ะ = เป็น handshake error ล้วน 100% |
| `COUNT_NAMEINFO_TRANSIENT/PERMANENT` | 0 / 1 ← DNS แทบไม่เกี่ยว |
| `COUNT_AUTHENTICATION_ERRORS` | 104 ← **ไม่ถูกนับเข้าโควตาบล็อก** |
| `COUNT_HOST_BLOCKED_ERRORS` | 2,735 ← ถูกปฏิเสธหลังบล็อกแล้ว ใน 6 วัน |

แถวของ `110.78.83.103` (ตัวเครื่องเอง) มี auth error 4 ครั้งแต่ connect error 0
→ **พิสูจน์ว่ารหัสผ่านผิดไม่ทำให้โดนบล็อก**

**เว็บไม่ล่ม** เพราะแอปต่อ DB จาก `110.78.83.103 → 110.78.83.103` วนในเครื่อง ไม่ผ่าน NAT
(NIC ถือ public IP ตัวนี้โดยตรง prefix /25 → gateway คือ `.1` พอดี)

**แก้ด้วย** `FLUSH HOSTS;` — ล้าง cache ในหน่วยความจำ ไม่แตะข้อมูล ไม่ต้อง restart

⚠️ **ยังไม่ได้แก้ต้นเหตุ** `max_connect_errors` ยังเป็น 100 จากสถิติจริง ~17 error/วัน
คาดว่า **จะโดนบล็อกซ้ำราว 19-20 ส.ค. 2569** — เข้าคิว `next:` แล้ว
เคยเกิดมาแล้ว 4 รอบ (4 มิ.ย. / 17 มิ.ย. / 20 ก.ค. / 7 ส.ค.) รอบล่าสุดค้างมา 6 วันโดยไม่มีใครรู้

รายละเอียดครบ + แผนย้อนกลับอยู่ที่ [runbook-mysql-host-blocked.md](runbook-mysql-host-blocked.md)

## 8. เปิด SSH เข้า prod

เดิมเข้าได้ทาง RDP อย่างเดียว ติดตั้ง OpenSSH Server แล้วใช้ key-based auth
(`Administrator@110.78.83.103`, key ที่ `C:\Users\azimuthotg\.ssh\emoneys_prod`)

กับดักที่เจอจริงระหว่างตั้ง 2 ข้อ — บันทึกไว้ใน `MEM.md` แล้ว:

1. บัญชีในกลุ่ม Administrators **ไม่ใช้** `~\.ssh\authorized_keys` ต้องใส่ที่
   `C:\ProgramData\ssh\administrators_authorized_keys` + ตั้ง ACL ให้เหลือแค่ SYSTEM/Administrators
   ไม่งั้น sshd เมินไฟล์ทั้งไฟล์แบบเงียบ ๆ
2. เขียนไฟล์ด้วย `-Encoding utf8` บน PowerShell 5.1 ได้ **BOM** นำหน้า → sshd อ่าน key ไม่ออก

## 9. ตั้งระบบสำรองฐานข้อมูล — เดิม**ไม่มีเลย**

ตรวจแล้วพบว่าเครื่อง prod **ไม่มี scheduled task, ไม่มีไฟล์ dump** มีแต่ binlog 6 ไฟล์
ซึ่ง **กู้อะไรไม่ได้ถ้าไม่มี full backup เป็นฐานตั้งต้น** — ใบสำคัญ 11,522 แถวไม่มีสำเนาใด ๆ

ตั้ง Scheduled Task `emoneys-db-backup` รันทุกวัน **02:00** ในนาม SYSTEM
สคริปต์ `C:\backup\backup-emoneys.ps1` อ่านรหัสจาก `.env` ตอนรัน ไม่ hardcode
ใช้ `--single-transaction` จึงไม่ล็อกตาราง เว็บใช้งานได้ระหว่างดัมป์

ทดสอบรันจริงแล้ว: dump 62.6 MB → zip **7.45 MB** ใน 6 วินาที `LastTaskResult = 0`
เก็บย้อนหลัง 30 วัน (~225 MB) สคริปต์ตรวจ 3 ชั้นก่อนถือว่าสำเร็จ
(exit code, บรรทัดท้ายต้องเป็น `Dump completed`, zip ต้องเปิดได้) จะลบ `.sql` ต่อเมื่อผ่านครบ

⚠️ ยังเหลือ: ไฟล์อยู่ดิสก์ลูกเดียวกับฐานข้อมูล, **ยังไม่เคยทดสอบ restore**, ไม่มี alert เมื่อล้ม

## 10. ปุ่ม re-sync ข้อมูล NPU รายคน — โค้ดชุดแรกที่ขึ้น prod

**อาการที่ผู้ใช้แจ้ง** บุคลากรย้ายจากคณะเทคโนโลยีอุตสาหกรรมไปวิทยาลัยพยาบาลบรมราชชนนีนครพนม
แต่ระบบยังโชว์หน่วยงานเดิม

**ต้นตอ** `_create_staff_user()` เขียน `department` จาก NPU **ตอนสร้างบัญชีครั้งเดียว**
ส่วน `_check_database_staff()` ที่ใช้ตอน login ครั้งต่อ ๆ ไป ตรวจแค่รหัสผ่าน ไม่เคย sync ซ้ำ
หลักฐาน: user id 34 มี `last_npu_sync` = `date_joined` เป๊ะ (31 ต.ค. 2568)
แต่ `last_login` = 6 ส.ค. 2569 — เข้าระบบมา 9 เดือนโดยข้อมูลไม่ขยับ
**ผู้ใช้ `npu_api` ทั้ง 1,352 คนอยู่ในสภาพเดียวกันหมด** และหน้าจัดการผู้ใช้ก็แก้ไม่ได้
เพราะปุ่มแก้ไขครอบด้วย `{% if user.source == 'manual' %}` (มีแค่ 48 จาก 1,400 คน)

**ทางออก** NPU มี lookup endpoint ที่ยืนยันสิทธิ์ด้วย **JWT อย่างเดียว ไม่ต้องใช้รหัสผ่านของเจ้าตัว**
ทดสอบจริงบน prod ได้ HTTP 200 และคืนหน่วยงานใหม่ถูกต้อง:

```
GET /v2/personnel/{staffcitizenid}/     GET /v2/student/{student_code}/
```

ชื่อฟิลด์เหมือน `personnel_info` / `student_info` ของ endpoint auth ทุกตัว
จึงห่อ response ให้เป็นรูปเดียวกันแล้วส่งต่อ `extract_user_data()` / `extract_student_data()`
เดิมได้เลย **ไม่ต้องเขียน mapper ใหม่**

**เลือกทำปุ่ม re-sync แทนหน้าฟอร์มแก้มือ** (ที่วางแผนไว้ตอนแรก) เพราะดึงจากต้นทางจริง
ไม่มีโอกาสพิมพ์ผิด และถ้ามีทั้ง 2 ทาง ค่าที่แก้มือจะขัดกับ NPU แล้วถูกทับตอน sync ครั้งถัดไป
**หน้าแก้ไขเดิมไม่ถูกแตะเลย** ยังเป็นของผู้ใช้ manual ต่อไป

การทำงานแบ่ง 2 จังหวะเสมอ: **GET = พรีวิว ไม่เขียนฐาน** แล้วแอดมินเห็นตารางเทียบก่อน
ค่อยกดยืนยัน → **POST = เขียนจริง** พร้อมบันทึกลง `UserActivityLog` action `npu_resync`

ผลทดสอบก่อน deploy (10 กรณี ผ่านหมด): พรีวิวเจอ 1 รายการถูกต้อง, GET ไม่เขียนฐาน,
POST เขียนแล้วฟิลด์อื่นไม่ขยับ, audit log ถูกต้อง, ยิงซ้ำได้ 0 รายการ (idempotent),
ผู้ใช้ manual ถูกปฏิเสธ 400, เลขบัตรไม่มีใน NPU ได้ 502 พร้อมข้อความบอกสาเหตุ,
คนไม่มีสิทธิ์ 403, ไม่ล็อกอิน 302, ค่าว่างจาก NPU ไม่ลบข้อมูลเดิมทิ้ง

## ข้อสรุประหว่างทางที่ผิดแล้วแก้แล้ว (ภาคบ่าย)

รอบนี้เดาผิด 3 เรื่อง บันทึกไว้เพื่อเตือนตัวเอง:

1. **เดาว่าสาเหตุการบล็อกคือ DNS** เพราะเห็น log
   `IP address '110.78.83.1' could not be resolved` — ตัวเลขใน `host_cache` ชี้ว่าเป็น
   handshake error ล้วน ส่วน nameinfo error มีครั้งเดียวและเป็นชนิดที่ไม่ถูกนับเข้าโควตา
2. **เดาว่าบอตจากอินเทอร์เน็ตยิงเข้ามาถมตัวนับ** — `host_cache` มีแค่ **2 แถว** จากที่จุได้ 279
   แปลว่าไม่มีใครจากข้างนอกยิงเข้ามาเลยนอกจากผ่าน NAT ตัวนั้น
   และคำเตือนเรื่อง "พอร์ตเปิดออกอินเทอร์เน็ต" ที่เคยพูดก็เกินหลักฐาน (ทดสอบได้แค่จากในเครือข่ายมหาลัย)
3. **สรุปว่า NPU API ทำ re-sync ไม่ได้** เพราะดูแค่ endpoint ที่โค้ดตั้งค่าไว้
   (`auth_and_get_personnel/` ที่บังคับต้องมีรหัสผ่าน) แล้วเหมาว่าไม่มีทางอื่น
   ของจริงมี lookup endpoint อยู่แล้ว — **อย่าสรุปความสามารถของ API ภายนอกจากโค้ดที่เราเขียนไว้**

เรื่องเล็กอีก 2: บอกว่า token ฝั่ง dev หมดอายุ (จริงคือสคริปต์ทดสอบผมอ่านมาขาด 1 ตัวอักษร)
และเคยบอกว่า `MEM.md` จดวิธีรัน prod ผิด (จริงคือ `MEM.md` ถูกอยู่แล้ว ผมเดาเองว่าเป็น `runserver`)
